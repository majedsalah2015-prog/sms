# 08 — Numbering Framework

**Phase:** 2 — Cross-cutting frameworks | **Status:** Draft for review | **Owner:** Software Architect + Senior Business Analyst

---

## 1. Purpose

Every official identifier (student number, receipt, certificate, application, employee number…) is generated by one configurable engine — per school, per document type — so numbering formats are sales configuration, never code (NF-M3), and financial sequences meet legal gap-free requirements (BR-GLB-041).

## 2. Format specification

A **numbering series** is defined by an ordered set of segments:

| Segment token | Meaning | Example |
|---------------|---------|---------|
| `{PREFIX}` | Fixed text (bilingual-capable for display; stored value is invariant Latin) | `STU`, `RCP` |
| `{SCHOOL}` | School short code | `AND` (Al-Andalus) |
| `{YEAR}` | Academic year label (configurable: `2026`, `26`, `2627`) | `26` |
| `{GYEAR}` | Calendar (Gregorian) year of generation | `2026` |
| `{SEQ:n}` | Zero-padded sequence, n digits | `00042` |
| `{SEP}` | Separator | `-`, `/` |

Example configurations: student `STU-{YEAR}-{SEQ:5}` → `STU-26-00042`; receipt `RCP/{SCHOOL}/{GYEAR}/{SEQ:6}` → `RCP/AND/2026/000117`.

## 3. Series behavior attributes

| Attribute | Options | Notes |
|-----------|---------|-------|
| Reset policy | Never / per academic year / per calendar year | Financial series usually per calendar year (tax alignment); student numbers **never** reset |
| Gap policy | **Strict (gap-free)** / normal | Strict: sequence issued only at successful posting, atomically — mandatory for receipts, invoices, refund vouchers |
| Scope | Per school (always) + optional sub-series (e.g., receipt series per cashier till) | Sub-series are visible in the number |
| Preview | Admin screen shows live sample before saving | Prevents misconfiguration |
| Locking | Format locked once ≥ 1 number issued; changes open a **new series** starting a chosen date | Historical numbers never reinterpreted |

## 5. Business rules

| ID | Rule |
|----|------|
| BR-NUM-001 | Numbers are generated only by the engine at the defined lifecycle moment (e.g., receipt number at posting, student number at admission approval) — never at draft, never manually (BR-GLB-040). |
| BR-NUM-002 | A generated number is immutable and never reused, including after cancellation — cancelled documents keep their number with status Void (BR-GLB-041/042). |
| BR-NUM-003 | Strict series are concurrency-safe with zero gaps: two simultaneous postings receive consecutive numbers; a failed posting never consumes a number. |
| BR-NUM-004 | The student number is a permanent identity — it survives withdrawal and re-admission (the returning student keeps their original number and file, per BR-GLB-002). |
| BR-NUM-005 | Series configuration and any new-series cutover are T1-audited (doc 07) and permission-gated to System Administration + Finance Manager approval for financial series (P2 workflow). |
| BR-NUM-006 | Numbers are searchable globally: entering any official number in global search resolves to its record (permission permitting). |
| BR-NUM-007 | Display formatting (e.g., Arabic-Indic digits) is presentation only; the stored number is the invariant canonical form. |
| BR-NUM-008 | Migration/import of legacy numbers is allowed into a dedicated closed legacy series (flagged, excluded from generation) so old documents remain referenceable. |

## 6. Screens

Series registry (list + status + last issued) · Series designer with live preview · Cutover wizard (close series, open successor) · Gap check report (strict series verification, for auditors).

## 7. Reports & widgets

Issued-numbers register per series/period · Void register (voided numbers with reasons) · Strict-series continuity certificate (auditor report: first, last, count, zero gaps) · Widget: today's receipts count (Finance dashboard).

## 8. Future enhancements

Check-digit support; QR payload standard (certificate/receipt verification links — coordinates with Certificates and Payments modules); per-branch sub-series for multi-school groups.

## 9. Open questions

1. Legal receipt/invoice numbering requirements per country pack (e.g., e-invoicing UUID coexistence with human numbers under ZATCA-style regimes) — pending README Q3; affects Payments module (Phase 6).
2. Student number format preference of pilot customers (year-embedded vs. flat sequence)? Year-embedded recommended for human context; flat is cleaner for lifelong identity — default proposal: flat `{SEQ:6}` with no year.
3. Should application numbers convert to student numbers (same number) or remain separate? Recommendation: **separate** — applications can be rejected; identity number should not inherit pipeline semantics.
